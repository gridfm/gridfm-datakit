## 2. Quantitative answers (@agent tags)

### Batch size for dynamic scheduling

| Scope | `dispatch_batch_size` | Why |
|-------|----------------------|-----|
| **Small** (IEEE + case500; millions of jobs) | **32** | `jobs/worker = n_pfs/p` is huge (e.g. case14 4M / 216 ≈ 18.5k). Fine-grained `batch=1` adds scheduling overhead; batch=32 keeps workers fed. |
| **Large** (case2000/10000; 10k–50k jobs) | **1** | Few jobs/worker at high `p` (e.g. 10k/168 ≈ 60). With batch=32 you get ~2 batches/worker → stragglers (`min_worker_completed=32`, `max=64`). Ablation (case2000, 10k, `--no-pf-fast`): batch=1 ~8–10% faster wall µs/solve at p≥72; ~tie at p=40. |

Rule of thumb used: `batch_size = max(1, min(32, floor(n_pfs / (p * 2))))`.  
Code: `dispatch_batch_size(scope) = scope == "small" ? 32 : 1` in `pure_julia/matrix_config.jl`.  
Details: `experiments/runtime/dispatch_batch_size_vs_parallelism.md`.

### Pure Julia vs Python + juliacall (must be quantitative)

Process-parallel **pure Julia** (`Distributed` + `pmap`) vs Python parent + `multiprocessing` + juliacall (same cached-base idea):

| Case / metric | Python+juliacall | Pure Julia | Ratio |
|---------------|------------------|------------|-------|
| case14 PF, wall µs/solve @ best p | ~33 µs (`n=1M`, p=24) | ~7 µs (`n=4M`, p=120) | **~4.7× faster** Julia wall |
| case14 PF, mean task runtime | ~584 µs (older p=168) | ~622 µs | ~1.07× (solve similar) |
| case14 PF, mean solve time | ~398 µs | ~452 µs | ~1.14× |

**Interpretation:** wall-time win is mostly **dispatch/IPC**, not Ipopt. For tiny solves, Python↔Julia bridge + multiprocessing dominates. For case2000 (solve ~0.65–0.75 s), wall µs/solve is nearly identical between Python pilot (10k) and Julia (50k) once scaled (~13.3 ms/solve).

**Decision:** all traditional-solver matrix work is pure Julia under `scripts/runtime/pure_julia/`.

### Solver choice: pf_fast

| Networks | PF setting | Reason |
|----------|------------|--------|
| case14–case500 | **`--pf-fast`** (`compute_ac_pf`) | Fast Newton-style PF; matches “quick” classical baseline. |
| **case2000, case10000** | **`--no-pf-fast`** (`solve_ac_pf` + **Ipopt**) | Fast PF is unreliable / not representative on large GOC; we intentionally use Ipopt AC PF. Mean solve ~0.65–0.75 s (case2000), ~tens of ms–hundreds for larger. |

**Wrong if you say “use fast PF for case2k/10k.”** Matrix config sets `pf_fast = false` for those two.

### Other things to keep in mind

1. **Sample counts** (shared with GENCO for fair wall ≥~20–30 s at fastest config): see §3. Same `n` for all modes per network in the full matrix (except counts differ by network).
2. **p sweep:** 24:16:216 → **13 points**. Report scaling curves; “fastest p” is usually mid/high p for small PF, not always p=216.
3. **Timing boundaries:** `pf_elapsed_s` = timed solve region only. Init (`init_elapsed_s`) and OPF prep (`opf_elapsed_s`) are **outside** that. Staging for s2 is also outside `pf_elapsed_s` but hits job wall time.
4. **Scenario pool size:** max **10_000** corrected JSONs; if `n_pfs > 10k`, indices wrap with modulo.
5. **Correction:** offline `correct_scenarios.jl` → `scenario_*_corrected.json`. Incomplete correction caused early s2 failures (`missing N corrected files`).
6. **`/tmp` staging required for s2.** Direct dccstor load inflated case14 load (~30–47× solve). After staging, parse in s2 case14 PF ~0.12–0.18 ms/solve.
7. **Stdout buffering** on LSF made s2 look “stuck” for minutes during staging; check CSV mtime/CPU, not only `.out` tails.
8. **Fork + juliacall / Julia after init is unsafe** — see `experiments/fork_shared_parse_not_viable.md`. Do not share parsed heaps via fork.
9. **OPF dominates wall** on small matrices (~4 h case14 OPF timed sum of 13 p-points). Throughput “slowness” of s2 vs s1 on PF is modest (~1.2–1.3×); OPF/DCOPF often ~parity.
10. **GENCO load-in-get** uses `--num-samples` = matrix count, `--max-preloaded-samples` = 10_000, modulo circle; batch ≤ 10k. Page-cache reuse is real but GENCO gap stays modest vs PM parse on small grids.

## 5. How to map to GENCO

| PowerModels | GENCO |
|-------------|--------|
| s1 cached-base | Preload samples in RAM; time inference only |
| s2 per-solve-load (+ /tmp stage) | Load-in-`get()` / fetch path inside timer |
| `n_pfs` | `num_samples` (same counts in matrix_aligned designs) |
| scenario modulo 10k | `max_preloaded_samples=10000` |
| `p` workers | Not 1:1 with GPU batch size — GENCO sweeps **batch size**; PM sweeps **process count** |
| `pf_elapsed_s / n_pfs` | Per-sample wall (outer_elapsed / num_samples) |
| pf_fast / Ipopt | Model tier + solver not analogous; compare at agreed sample counts |

**Fair comparison checklist for the GENCO agent:**

1. Same networks and same `n` as `matrix_config.jl`.
2. Same “in timer / out of timer” philosophy for preload vs load-in-get.
3. Do not compare GENCO batch-size curves to PM `p` curves without stating they measure different axes.
4. On case14-class grids, expect PM s2 parse to hurt more than GENCO disk fetch relative to compute.
5. On case2000/10k PF, expect s1≈s2 for PM (solve dominates); GENCO differences may still be small.

## 7. Short verdict for the table

- **s1** = base scenario in RAM (parse/prep outside timer) — run and recommended for solver-centric comparison.  
- **s2** = datakit scenarios from `/tmp` with parse inside timer — run; required for end-to-end story; staging + FS effects are first-class.  
- **Datakit-all-in-RAM × many processes** — not used; memory-prohibitive.  
- **Batch:** **32** small, **1** large.  
- **Stack:** pure Julia, not Python+juliacall (~5× wall on case14 PF).  
- **Large GOC PF:** **Ipopt / no pf-fast**, not fast PF.
